## 📌 주요 기능

<a id="feature-1"></a>

<details>
<summary><b>사용자</b> — 이승현</summary>
<br>

<img width="700" alt="사용자 API" src="docs/images/api/user.png" />

### ✨ 기능

- 회원가입 · 로그인 · 사용자 정보(닉네임) 수정
- 이메일 중복 검사 및 입력값 검증
- 사용자 논리 삭제(탈퇴)
- 논리 삭제 후 일정 기간 경과 시 연관 데이터와 함께 물리 삭제
- 요청 헤더 기반 사용자 식별

### 💡 구현 포인트

- 활성 사용자 조회: 탈퇴(논리 삭제)한 사용자는 로그인 · 조회 대상에서 빠지도록 사용자 조회를 활성 사용자 기준으로 통일하고, 여러 명을 한 번에 조회하는 메서드도 제공 ([#128](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/128), [#179](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/179), [#181](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/181))
- 이벤트 발행: 가입 · 닉네임 수정 · 물리 삭제 시 이벤트를 발행해, 활동 내역 등 다른 도메인이 사용자 코드에 직접 의존하지 않고 후속 처리 ([#185](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/185), [#200](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/200))

    - Job마다 `JobConfig` · `Scheduler` · `Listener` · `Metrics`로 나눠 같은 구조로 구성
- **커밋된 건수만 메트릭에 반영**
    - 성공 건수는 청크 커밋 뒤(`afterChunk`)나 Step 완료(`COMPLETED`) 때만 올려, 롤백된 작업이 숫자에 섞이지 않게 함
    - 메트릭: `batch.article.collection.*` · `batch.article.backup.uploaded.articles` · `batch.notification.cleanup.deleted` · `batch.user.cleanup.deleted` · `batch.log.backup.*`

    - RSS 3곳은 Step마다 한 번만 받아 관심사별로 재사용하고, Naver는 키워드마다 호출
    - 외부 API 실패는 출처별 실패 메트릭만 올리고 나머지 관심사 수집 · 저장을 마친 뒤, Job을 `FAILED`로 표시
- **S3 백업 재시작** ([#317](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/317))
    - 기사 · 로그 백업은 마지막 커서와 파일 번호를 `ExecutionContext`에 저장해, 실패 후 같은 날짜로 다시 실행하면 실패한 파일부터 이어서 업로드
    - 이미 완료된 날짜는 다시 실행되지 않아 같은 파일이 중복 업로드되지 않음
- **로그 백업** ([#266](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/266), [#317](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/317))
    - 전날 로그 파일을 10개씩 묶어 tar.gz로 압축한 뒤 `logs/{날짜}/` 아래에 업로드
    - 전체 파일 수 · 업로드된 파일 수를 메트릭으로 남겨 누락 여부 확인
- **사용자 완전 삭제: 이미 지운 사용자는 유지** ([#317](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/317))
    - Step 전체를 한 트랜잭션으로 묶지 않아(`ResourcelessTransactionManager`), 100명 단위로 커밋한 삭제가 뒤의 실패로 함께 롤백되지 않게 함

    - 20명이 동시에 좋아요를 누르면 좋아요 행은 20개인데 `like_count`는 3으로 남는 갱신 손실을 테스트로 확인

- **삭제와 카운트 정합성** ([#254](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/254))
    - 조건부 UPDATE로 동시 삭제 중 한 요청만 성공 처리해 기사 댓글 수가 두 번 줄지 않게 함
    - 물리 삭제 시 좋아요와 좋아요 알림도 함께 삭제
    - `CHECK` 제약으로 좋아요 수 · 댓글 수가 0 아래로 내려가지 않게 DB에서 한 번 더 방어
- **댓글 수정 시 좋아요 수 보존** ([#254](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/254))
    - 수정 시 바뀐 컬럼만 저장해, 동시에 눌린 좋아요 수를 덮어쓰지 않게 함
- **커서 페이지네이션** ([#292](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/292))
    - 마지막 댓글 id를 커서로 쓰고, 정렬 값 → 작성 시각 → id 순으로 비교해 값이 같은 댓글도 누락 · 중복 없이 조회
- **사용자 완전 삭제 시 카운트 정리** ([#302](https://github.com/SB14-HJ3S/sb14-monew-team03/pull/302))

    - 이미 논리 삭제된 댓글은 그때 줄였으므로 차감 대상에서 제외

## 📌 주요 처리 흐름 (최종 구현 후 수정 예정)

<details>
<summary><b>1. 요청자 확인</b></summary>
<br>

```text
API 요청 (헤더: Monew-Request-User-ID)
   ↓
RequestIdInterceptor
   ↓   @RequestId가 붙은 API만
헤더 값을 UUID로 확인
   ↓
RequestIdContext에 요청자 ID 저장
   ↓
서비스에서 요청자 ID를 꺼내 사용
   ↓   요청이 끝나면
RequestIdContext 비우기
```

- **@RequestId**: 요청자가 필요한 API에만 붙이는 표시. Swagger에도 헤더 입력칸이 자동으로 생김
- **잘못된 헤더**: 비어 있거나 UUID 형식이 아니면 400 에러
- **RequestIdContext**: 요청마다 따로 쓰는 저장 공간(ThreadLocal)이라 다른 사람의 요청과 섞이지 않음

</details>

<details>
<summary><b>2. 관심사 유사 이름 검사</b></summary>
<br>

```text
관심사 등록 요청 (이름 · 키워드)
   ↓
이름 정규화 (공백 제거 · 소문자 · 한글 자모 분리)
   ↓
기존 관심사 이름과 유사도 계산 (레벤슈타인 거리)
   ↓
80% 이상 비슷하면 등록 불가 (409)
   ↓   아니면
관심사 · 키워드 저장
```

- **유사도**: 두 이름을 같게 만들려면 몇 글자를 고쳐야 하는지로 계산
- **자모 분리**: "트렌드"와 "트랜드"처럼 한 글자 안의 모음만 달라도 차이를 잡아냄
- **예시**: 기존 "AI 트렌드"가 있으면 "AI 트랜드"는 등록 불가

</details>

<details>
<summary><b>3. 뉴스 기사 자동 수집</b></summary>
<br>

```text
매시간 정각 Spring Batch 수집 Job 실행 (@Scheduled + ShedLock)
   ↓
구독 중인 관심사 · 키워드 조회
   ↓
네이버 뉴스 API · 언론사 RSS 기사 수집
   ↓
키워드가 들어간 기사만 선별
   ↓
원본 URL 기준 중복 제거
   ↓
관심사별 기사 저장
   ↓   새 기사가 있으면
구독자에게 알림 생성
```

- **ShedLock**: 배포 중 앱이 2개 떠 있어도 한 번만 실행
- **언론사 RSS**: 한국경제 · 조선일보 · 연합뉴스
- **관심사별 저장**: 한 관심사가 실패해도 다음 관심사는 계속 수집
- **알림 생성**: `ArticlesSavedEvent` 발행 → 커밋 후 비동기로 생성

</details>

<details>
<summary><b>4. 댓글 좋아요 → 알림</b></summary>
<br>

```text
댓글 좋아요 등록
        ↓
CommentLikedEvent 발행
        ↓
Transaction COMMIT
        ↓
@TransactionalEventListener(AFTER_COMMIT) + @Async
        ↓
댓글 작성자에게 Notification 생성
```

</details>

<details>
<summary><b>5. 사용자 활동 내역 (구현 후 수정 예정)</b></summary>
<br>

```text
댓글 · 좋아요 · 기사 열람 · 구독 발생
        ↓
활동 이벤트 발행
        ↓
MongoDB 사용자 활동 문서 갱신
        ↓
활동 내역 조회 시 문서 1건으로 응답
```

</details>

<details>
<summary><b>6. 논리 삭제 → 물리 삭제 (구현 후 수정 예정)</b></summary>
<br>

```text
삭제 요청
   ↓
논리 삭제 (삭제 시각만 기록)
   ↓   이때부터 조회 · 목록에서 제외, 데이터는 유지
물리 삭제
   ↓
관련 데이터도 함께 삭제
```

| 도메인 | 물리 삭제 시점 | 함께 삭제되는 관련 데이터 |
|---|---|---|
| **사용자** | 논리 삭제 후 1일 지나면 배치가 자동 삭제 | 구독 · 댓글 · 좋아요 · 알림 · 기사 조회 기록 (구독자 수도 정리) |
| **뉴스 기사** | 물리 삭제 API (`/hard`) | 댓글 · 댓글 좋아요 · 좋아요 알림 · 기사-관심사 연결 · 조회 기록 |
| **댓글** | 물리 삭제 API (`/hard`) | 좋아요 (기사의 댓글 수도 정리) |

- **논리 삭제가 기본**: 관련 정보가 남아 있도록 바로 지우지 않음
- **사용자 물리 삭제**: `UserHardDeletingEvent`를 발행해서, 사용자 도메인이 다른 도메인 코드를 직접 부르지 않고 이벤트로 정리를 맡김
- **기사 · 댓글 물리 삭제**: 화면(UI)에는 없고 API와 테스트 코드로 검증

</details>

<details>
<summary><b>7. 데이터 정리 배치 (구현 후 수정 예정)</b></summary>
<br>

```text
매일 새벽 3시                          매시간 정각
   ↓                                    ↓
확인 후 7일 지난 알림 조회              논리 삭제 후 1일 지난 사용자 조회
   ↓                                    ↓
알림 삭제                               사용자와 관련 데이터 물리 삭제
```

</details>

<details>
<summary><b>8. 기사 백업 · 복구 (구현 후 수정 예정)</b></summary>
<br>

**백업**

```text
매일 0시 Spring Batch 실행
   ↓
전날 저장된 기사 조회 (1,000건씩)
   ↓
JSON 직렬화 + gzip 압축
   ↓
Amazon S3 업로드 (날짜별 · 파트별 .json.gz 파일)
```

**복구**

```text
복구 요청 (날짜 범위)
   ↓
S3 백업 파일 조회
   ↓
DB에 없는 기사 선별
   ↓
유실 기사만 복원
```

</details>

<details>
<summary><b>9. CI/CD</b></summary>
<br>

```text
PR 생성
   ↓
CI 검사 + 자동 리뷰
   ↓   CI 통과 · 리뷰 승인
develop 머지
   ↓   develop CI 성공 시 자동 배포
Docker 이미지 빌드
   ↓   OIDC로 AWS 인증
Amazon ECR 업로드
   ↓
Amazon ECS 무중단 배포
```

- **CI 검사 (GitHub Actions)**: 빌드 · 테스트, Checkstyle · ArchUnit 패키지 규칙, JaCoCo 커버리지 → Codecov
- **자동 리뷰**: CodeRabbit · Claude Code
- **OIDC 인증**: GitHub Actions에 AWS 키를 저장하지 않고, 배포할 때만 잠깐 쓰는 권한을 받음
- **무중단 배포**: 새 버전이 정상으로 뜬 뒤에 옛 버전 종료

</details>

## 📌 개발 규칙

> 자세한 컨벤션은 [팀 Notion](https://app.notion.com/p/8949e310974382de9473015def3c352b)을 참고합니다.

<details>
<summary>[펼쳐보기]</summary>

| 구분 | 규칙 |
| :--- | :--- |
| 브랜치 전략 | `{타입}/{이슈번호}-{작업명}` → `develop` → `main` (예: `feat/12-interest-subscribe`) — 이슈의 Branch Keyword 칸에 작업명을 적으면 브랜치가 자동으로 생성됨 |

| PR 규칙 | 이슈 연결(`close #이슈번호`) · 리뷰 승인 1명 이상 후 **일반 머지가 기본**(TDD 단계 커밋을 develop에 그대로 남김) |
| 코드 스타일 | Spotless(google-java-format `aosp()`, 들여쓰기 4칸) — 커밋 시 Git Hook으로 자동 적용, **최종 포맷 기준**. push 전에는 포맷 검사 · 컴파일을 한 번 더 확인 |
| 협업 자동화 | PR 제목 · 라벨 자동 정리, 이슈 · PR · 리뷰 디스코드 알림, 프로젝트 보드 상태 자동 변경 |
| 기본 에디터 설정 | `.editorconfig` — 인코딩(UTF-8)·줄바꿈(LF)·줄 끝 공백 제거 등을 에디터 종류와 무관하게 통일 (IntelliJ 포함 대부분의 에디터가 자동 인식) |
| 저장 시 자동 포맷팅 | 인텔리제이를 **닫은 상태**에서 `./gradlew installIntellijActionsOnSave` 1회 실행 (Java 파일 저장할 때마다 리포맷 + import 정리 — 편의용이며, 커밋 시 Spotless가 다시 한 번 기준에 맞춰 정리함) |

## 📌 로컬 개발 환경 구동 방법

> IntelliJ 설정까지 포함한 단계별 안내는 [SETUP.md](./SETUP.md)에 있습니다.

<details>
<summary>[펼쳐보기]</summary>
<br>

**요구사항**

- JDK 17
- Docker Desktop (실행 중이어야 함)

**1. 저장소 받기**

```bash
git clone https://github.com/SB14-HJ3S/sb14-monew-team03.git
cd sb14-monew-team03
```

**2. 환경 변수**

`.env.example`을 복사해 `.env`를 만들고 값을 채웁니다.

```bash
cp .env.example .env
```

| 값 | 용도 |
| :--- | :--- |
| `AWS_ACCESS_KEY_ID` · `AWS_SECRET_ACCESS_KEY` · `AWS_S3_BUCKET` | 로컬에서 S3 기능(기사 백업 · 복구, 로그 적재) 테스트용 — 로컬 전용 버킷 |
| `NAVER_API_CLIENT_ID` · `NAVER_API_CLIENT_SECRET` | 뉴스 수집용 네이버 API 키 |

> 비밀값은 저장소에 커밋하지 않습니다. (`.env`는 `.gitignore`에 등록)<br>
> 로컬 DB 접속 정보는 `compose.yaml`에 고정돼 있어서 `.env`에 적지 않습니다.

**(선택) direnv로 쉘에도 자동 연동**

`.env`는 스프링 앱에만 읽히므로, 터미널에서 `aws` CLI 등 외부 명령어도 같은 값으로 쓰려면 [direnv](https://direnv.net/)를 추가로 설정합니다. 저장소의 `.envrc`가 `.env`를 자동으로 불러옵니다.

```bash
brew install direnv
# 쉘 설정 파일(.zshrc 등)에 추가 후 터미널 재시작
echo 'eval "$(direnv hook zsh)"' >> ~/.zshrc
direnv allow   # 프로젝트 폴더에서 한 번만 실행
```

**3. 로컬 인프라**

앱을 실행하면 `compose.yaml`의 DB · 모니터링 컨테이너가 자동으로 같이 뜹니다. 직접 띄우려면:

```bash
docker compose up -d
```

| 서비스 | 주소 |
| :--- | :--- |
| PostgreSQL 16 | `localhost:5432` (DB `monew`) |
| MongoDB 7 | `localhost:27017` (DB `monew`) |
| Prometheus | `localhost:9090` |
| Grafana | `localhost:3000` |

**4. 애플리케이션 실행**

```bash
# macOS / Linux
./gradlew bootRun

# Windows
.\gradlew.bat bootRun
```

| 대상 | 주소 |
| :--- | :--- |
| 웹 화면 | http://localhost:8080 |
| Swagger UI | http://localhost:8080/swagger-ui/index.html |
| OpenAPI JSON | http://localhost:8080/v3/api-docs |
| 서버 상태 | http://localhost:8080/actuator/health |

**5. 테스트**

```bash
./gradlew test
```

> 테스트는 Testcontainers(PostgreSQL · MongoDB)로 실행되며, 커버리지 리포트(JaCoCo)가 함께 생성됩니다. Docker Desktop을 켜 두세요.

**6. 종료**

```bash
docker compose down
```

> 로컬 데이터까지 지워야 할 때만 `docker compose down --volumes`를 실행합니다.
